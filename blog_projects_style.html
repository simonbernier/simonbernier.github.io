1. How your site works (30-second version)

Your repository holds source files (Markdown text + settings). Every time you push to the main branch on GitHub, a robot (GitHub Actions) runs Jekyll, which converts those files into the finished website and publishes it. You never edit HTML pages of the site directly — you edit Markdown files and Jekyll does the rest.

Folder / fileWhat it is
_pages/The site's main pages: about (homepage), cv, publications, blog, projects.
_posts/Your published blog posts. One file = one post.
_drafts/Unpublished posts. Invisible on the live site. Currently holds 31 theme examples you can learn from.
_projects/Your project entries. One file = one project card.
_bibliography/papers.bibYour publications (BibTeX). Feeds the publications page.
assets/img/Images used by pages, posts and projects.
_sass/The stylesheets — colors, fonts, spacing (see section 5).
_config.ymlSite-wide settings. Small edits, big effects — change one thing at a time.
_layouts/, _includes/The theme's page templates. You rarely need to touch these.
_site/Generated output of a local build. Never edit it; it is ignored by git and rebuilt from scratch every time.

2. Golden rules — how to never break the site

  1. Make changes on a branch, not directly on main. Create a branch (git checkout -b my-change), push it, and open a Pull Request on GitHub. The Deploy site check builds your version without publishing it — if the check is green, merging is safe.
  2. Never change the filename or permalink of something already published. That changes its web address and breaks links people may have saved.
  3. Name files in lowercase with hyphens, no spaces or accents: ma-premiere-eval.md, not Ma Première Éval.md. (Filenames become URLs.)
  4. One logical change per commit, with a message saying why. If something breaks, git revert undoes exactly that change.
  5. Don't commit stray files to the repository root. Anything not listed under exclude: in _config.yml gets published on the live site. (This guide is in the exclude list for that reason.)

3. Adding blog posts

One-time setup: re-enable the blog page

The blog page exists but is switched off. Open _pages/blog.md and delete this single line near the top, then commit:

published: false # page is disabled for now; ...

That restores the blog tab in the navigation bar and the post list at /blog/.

Also do this: in _pages/about.md, set latest_posts: enabled: true to bring back the "latest posts" section on your homepage — it was turned off while the blog page was disabled so it wouldn't link to a missing page.

Writing a post

  1. Create a file in _posts/ named YYYY-MM-DD-short-title.md (the date prefix is mandatory — Jekyll silently ignores files without it). Example: 2026-07-10-fine-tuning-basics.md.
  2. Start the file with front matter (the block between --- lines), then write your text in Markdown below it: 
    ---
layout: post
title: "Les bases du fine-tuning"
date: 2026-07-10
description: "Ce que j'ai appris en ajustant mon premier modèle."
tags: [ia, apprentissage]
categories: ia-securite
---

Votre texte ici, en Markdown. **Gras**, *italique*,
[liens](https://example.com), listes, etc.
  3. Commit, push, done. The post's address will be /blog/2026/fine-tuning-basics/ (year + filename, from the permalink setting in _config.yml).

Useful extras

  • Not ready to publish? Put the file in _drafts/ instead (date prefix optional there). Drafts never appear on the live site. Move the file to _posts/ when ready.
  • Learn from the examples: the 31 files in _drafts/ are theme demos showing math (2015-10-20-math.md), code blocks, images, tables of contents, charts, and more. Open one, copy the front-matter options you need into your own post.
  • Images: put them in assets/img/ and reference them with: 
    {% include figure.liquid path="assets/img/mon-image.jpg" class="img-fluid rounded" %}
    or plain Markdown: ![description](/assets/img/mon-image.jpg).
  • Math: already enabled site-wide. Write $$ E = mc^2 $$ for display math.
  • Tag buttons on the blog page: display_tags and display_categories in _config.yml still list the theme's demo tags — replace them with the tags you actually use (or leave empty lists).
Watch out: a post dated in the future won't appear until that date passes. If a new post is missing, check its date and filename format first.

4. Adding projects

One-time setup (two small edits)

  1. In _pages/projects.md, delete the published: false ... line — this restores the projects tab and the card grid at /projects/.
  2. In _config.yml, find the collections: block and change output: false to output: true for projects. Why: each project card links to its own detail page; with output: false those pages don't exist and every card would lead to a dead link.

Creating a project

Create a file in _projects/, e.g. eval-llm-securite.md:

---
layout: page
title: "Évaluation de sécurité d'un LLM"
description: "Une phrase qui apparaît sur la carte du projet."
img: assets/img/mon-projet.jpg   # optional card image; omit the line for no image
importance: 1                    # 1 shows first, 2 second, ...
category: work                   # must be one of the categories below
---

Full description of the project in Markdown — goals, methods, results, links.
  • Categories: the projects page groups cards by the list in _pages/projects.md front matter: display_categories: [work, fun]. Rename these to whatever suits you (e.g. [ia-securite, physique]) — just make each project's category: match one of them.
  • The demo projects: _projects/1_project.md … 9_project.md are theme examples. Delete them (or keep one as a template) before you re-enable the page, otherwise they'll appear alongside your real work.

5. Changing the style

Easy wins — settings in _config.yml

SettingEffect
icon: ⚛️The favicon (browser-tab icon). Any emoji works.
max_width: 930pxHow wide the content column is.
blog_name, blog_descriptionTitle and subtitle shown at the top of the blog page ("Le blog / un espace pour apprendre et partager").
footer_text, descriptionFooter line and the site description used by search engines — both still contain theme placeholder text you may want to personalize.
enable_darkmode: trueShows the light/dark toggle in the navbar.

Colors — _sass/_themes.scss and _sass/_variables.scss

The single most visible choice is the accent color (links, buttons, highlights). It is set in _sass/_themes.scss, once for light mode (the :root block) and once for dark mode (the html[data-theme="dark"] block further down):

--global-theme-color: #{$purple-color};   /* the accent color  */
--global-hover-color: #{$purple-color};   /* links on hover    */

Swap $purple-color for any variable defined in _sass/_variables.scss ($blue-color, $green-color, $red-color, …), or define your own there first:

$mcgill-red: #ed1b2f !default;

then use #{$mcgill-red} in _themes.scss. Change one value, rebuild/preview, judge, repeat.

Which stylesheet does what

FileControls
_sass/_variables.scssThe color palette and basic measurements — edit values here first.
_sass/_themes.scssWhich colors are used where, separately for light and dark mode.
_sass/_base.scssEveryday elements: text, headings, links, tables, figures, post list. Add your own custom CSS rules at the end of this file.
_sass/_layout.scssPage structure: header, footer, spacing.
_sass/_cv.scss, _distill.scss, _tabs.scssStyles specific to the CV page, Distill-style posts, and tab widgets.

Fonts

The theme loads Roboto from Google Fonts. To change it, edit the google_fonts URL under third_party_libraries: in _config.yml (pick a font on fonts.google.com and copy its CSS URL), then update the font-family rule in _sass/_base.scss.

More recipes: the repo's own CUSTOMIZE.md file documents every theme option in detail — it's the theme's official customization manual.

6. Previewing your changes

Option A — locally (fast feedback)

Ruby is installed on this computer (since 5 July 2026). From the repository folder, run:

bundle exec jekyll serve --disable-disk-cache

then open http://localhost:4000. The site rebuilds automatically each time you save a file (refresh the browser). Press Ctrl+C to stop.

Two known local limitations (harmless): responsive image generation (needs ImageMagick) and JavaScript minification (needs Node.js) are skipped locally. GitHub performs both when it builds the real site, so the live result can look marginally more polished than your preview.

Option B — the safety net (recommended for anything risky)

  1. git checkout -b my-change — work on a branch.
  2. Commit and git push -u origin my-change.
  3. Open a Pull Request on GitHub. The Deploy site check does a complete production build without publishing anything.
  4. Green check → merge → the live site updates in ~2 minutes. Red check → click it to read the error; the live site is untouched.

7. Troubleshooting

SymptomMost likely cause
New post doesn't appearFilename missing the YYYY-MM-DD- prefix, or the date is in the future, or the file is in _drafts/.
Site didn't update after pushingCheck the Actions tab on GitHub — the build may still be running or may have failed (open the log; the error message names the file at fault).
Page shows raw {% ... %} textA typo in a Liquid tag — compare against the example you copied from.
Whole site looks broken after a config changeYAML is indentation-sensitive: check you used spaces (never tabs) and kept the exact indentation of neighbouring lines. Revert the commit if unsure.
Old page still shows in the browserHard refresh (Ctrl+F5) — browsers cache aggressively.
